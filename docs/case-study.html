Reading and writing

  • Writes are strict. Unknown keys, empty keywords or a group that doesn't exist: rejected (422).
  • Reads are tolerant. An unknown key or a dead rule is skipped and logged. The page never breaks.
  • Saves merge. Saving required fields keeps the rules.
  • One reader. Every part of the code calls load_settings(org).
  • Admins only. The server stamps who and when on each rule.

How a rule hits

  • Checked line by line, top of the list first. First hit wins.
  • max_amount set: only lines at or under that total.
  • Lines hit different rules: the highest-value line decides. Flagged.
  • A hit locks the group. The classifier never runs.
  • A buyer or admin can override. Logged with the rule ID.

Keyword matching, German and English

  • A rule lists its words in both languages. No translation step.
  • Both sides are cleaned the same way: lower case, ä ö ü ß become ae oe ue ss, hyphens and punctuation become spaces.
  • A one-word keyword hits a word that starts or ends with it. So toner hits "Tonerkartusche" and "Druckertoner".
  • A keyword of several words must appear in that order. Each word may run longer, so cable tie hits "cable ties".
  • Keywords under 4 letters must match the whole word.
  • Near misses are tests: "Kabeltrommel", "printer" and "ERP licence" must hit nothing.
  • More languages later: add keywords, or a new cleaning step. The rule shape stays.

Eval first One function for two lists.

What the key says is right

  • Total is the net cost Acme pays: items plus shipping and fees, before VAT.
  • Shipping and fees are lines, so the lines add up to the total.
  • Alternatives are not lines. Neither are headings with no price.

  • Vendor: the company that sent the quote. Umlauts and case ignored.
  • Numbers: equal to the cent.
  • Title, department and group: logged, not scored.

  • Shortlist: code, not AI. About 15 of the 380 real group names. Shared with Problem 2. How it searches is picked by an eval: Shared search.
  • Word match always works with no API key, so tests stay offline and nothing changes in the database.
  • Classifier: sees short aliases G1…G15 plus NONE, locked by the output schema. Code maps them back to real IDs. It can't return an ID that doesn't exist.
  • Every save re-checks rules, create and edit. The dropdown or an agent can't get round them.
  • Override: only a buyer or admin can keep a different group. It is logged with the rule ID.
  • Every result says why: rule, model or person.

Target design: works at millions of rows

The list is never sent to the model. Find a few candidates with cheap, indexed lookups, then let the model pick from those only. The prompt stays the same size at 2,000 or 2 million rows.

1. Exact matches first (no AI)

  • Company rules (Acme: cable ties → Electrical Engineering).
  • Supplier article number or EAN.
  • Past decisions: same company, same item text → same group.
  • Instant and certain at any size. Many lines end here.

2. Find candidates (no AI)

  • Keyword search on names and codes: "HP 305A", "Kabelbinder 200mm".
  • Meaning search (embeddings, stored once per row): "Kabelbinder" ↔ cable ties, "Notion team plan" ↔ software subscription.
  • Filter first by company, supplier or top-level category.
  • Combine both, keep the top 20–50. Milliseconds at millions of rows. Postgres with pgvector can do this.

3. Model picks from the shortlist

  • Gets the line item and ~20 candidates, never the full list.
  • Must return one of those IDs, checked in code, plus a confidence.
  • Can't invent an ID. Anything off the shortlist is rejected.

4. Low confidence → a person

  • They pick from the same shortlist, not a 2,000-option dropdown.
  • Their choice is saved and becomes an exact match next time.

Shrink the problem up front

  • Clean up the padded list: one "Toner Cartridges" group, with Bulk or Pallet as attributes. About 5× fewer rows.
  • Use the hierarchy: pick the top-level category, then search inside it.
  • Same pattern solves Problem 2: suggesting catalogue articles is the same search over a bigger list.

Approval Limit

No buyer sign-off under €2,000

Acme said

"Anything below €2,000 shouldn't need approval at all."

Do we have tests?

Built 10 Nov

  • 50 backend tests in tests/test_approval.py: the rule, the setting, create, edit and the seed.
  • 4 frontend tests for the "Auto" label. Full backend suite: 324 passed.

How it works today

  • Every new request starts as pending.
  • A buyer or admin sets it to approved or rejected. Once only.
  • The total is total_cost on the request.
  • Gap we found: any member, even a requester, can set the status to closed. Even before approval. Decided 10 Nov: its own fix, not part of this bonus.

Tests to write first

All pass

  • €1,999.99 is approved on create.
  • €2,000.00 stays pending.
  • No total stays pending.
  • The total is added up from the lines in code. The total the form sends is ignored.
  • Lines that don't add up to the printed total: never auto-approved.
  • Auto-approval writes "auto-approved" to the activity log.
  • Editing an approved request above €2,000 sends it back to pending.
  • Another company without a limit keeps today's behaviour.

Decisions

Decided 10 Nov

  • Total added up in code. The limit is checked against it, never the total the form sends.
  • Net, not gross. €2,000 means the total before VAT. Why: the request total is the net cost everywhere else (Problem 1), and typed requests have no VAT to add.
  • Strictly below. €1,999.99 is approved on its own. €2,000.00 still needs a buyer. Why: Acme said "below".
  • A company setting, no screen yet. approval_limit in the company settings, next to the rules. Acme gets 2000. No limit set keeps today's behaviour.
  • The closing gap is its own fix. Not part of this bonus. Logged under Later.
  • Edits follow the same rule as create. A pending request edited below €2,000 approves on save.
  • A buyer's no stays a no. Editing never overturns a rejection.
  • A buyer's yes resets only if the total rises. Same or lower stays approved. An auto-approved request edited to €2,000 or more goes back to pending.
  • Both are recorded. Auto-approval sets the approval time and logs auto_approved. Going back to pending clears the time and logs approval_reset with the old and new totals.
  • The strict totals check blocks it. Lines against the printed net, as saved today. A misread net waits for a buyer. Safe side.

Later

  • An admin screen to set the limit.
  • Use the form's gross check at save too, so correct quotes stop waiting for a buyer.
  • Clearing the limit through the API drops the key, so the seed puts €2,000 back on the next start. Store an empty limit instead.
  • Stop requesters closing a request, and stop anyone closing one before approval.
  • Splitting one order into small ones to stay under the limit. Not solved. Flag it to Acme.
