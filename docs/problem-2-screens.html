Commodity Rules
Checked top to bottom on every line, on every save. The first rule that fits wins. Lines no rule fits go to the model.
Add

As Requester the group is just set automatically. Tap "Send another group" to see a save corrected quietly. Switch to Buyer or Admin to see which rule set it: add Toner to see two rules hit, raise the Abo quantity past €500 and the model takes over, clear the lines and add USB-C Adapter for a low-confidence pick. Buyer can override, Admin can edit rules.

Contract

  • Rule: { id: string (server-set), keywords: string[] (non-blank, EN or DE), commodity_group_id: int, reason: string (default ""), max_amount: decimal string | null (EUR, line total, inclusive), updated_by: { id: uuid, name: string }, updated_at: datetime }.
  • Rules list: GET /organizations/me/settings returns commodity_rules: Rule[] in match order. PATCH /organizations/me/settings with { commodity_rules: [...] } (admin only, merges other keys) replaces the list; array order is the new order; the server sets id for new rules and updated_by/updated_at for changed ones. Errors: 422 { detail: [{ loc, msg }] } for blank keywords or unknown group; 403 for non-admins.
  • Live categorise: POST /categorise with { lines: [{ id: uuid, description: string, quantity: number, unit_price: decimal string }], rules?: Rule[] } (rules only from admins, to test an unsaved list) returns Categorisation. No save. The form calls it debounced on line edits; the rules test box calls it with one line.
  • Per line: { line_id: uuid, line_total: decimal string, group_id: int | null, source: "rule" | "model" | "none", rule_id: string | null, matched_keyword: string | null, rule_used: bool, skipped_rules: [{ rule_id, why: "over_max_amount" }], confidence: number | null (0 to 1, model only), suggestions: [{ group_id: int, name: string, confidence: number }] (top 3, model only) }.
  • Request level (in Categorisation and on request detail as commodity): { group_id: int | null, source: "rule" | "model" | "person" | "override", rule_id: string | null, decided_by_line: uuid | null, locked: bool, needs_person: bool, can_override: bool (from role), conflict: { rule_ids: string[], winner_rule_id: string, winner_line: uuid } | null, override: { from_group_id: int, to_group_id: int, reason: string, by: { id, name, role }, at: datetime } | null }. needs_person when the top confidence is under the threshold (server constant, proposed 0.7). Rule fields are returned to every role; the UI shows them only to buyers and admins and tells requesters "Set automatically".
  • Save payload (create and edit) adds: commodity_group_id: int, commodity_source: "rule" | "model" | "person", commodity_override: { group_id: int, reason: string } | null (buyers and admins, later). On every create and edit the server re-runs the rules; when a rule fits, it saves the rule's group whatever the client sent.
  • Save response: the request with commodity: { group_id: int, source: "rule" | "model" | "person", rule_id: string | null, corrected: bool } (source: "override" once 3.2 ships). rule_id is filled for every role; corrected is true when the server changed the group the client sent.
  • No rule error: a group that disagrees with a rule is corrected, never rejected, for requesters and agents alike; an override sent by a requester is ignored the same way. Remaining errors, shape { detail: { code, message } }: group_required (422, model not sure and nobody picked) and, with 3.2, override_reason_required (422).
  • Activity: on create or edit, RequestActivity.detail.categorisation = { lines: per-line objects above, request: request-level object above }. When the server corrected the group it also logs RequestActivity.detail.commodity_correction = { from_group_id: int, to_group_id: int, rule_id: string }. Feeds the problem 4 flags group_rule_overridden and group_low_confidence.
  • Groups: the existing GET /commodity-groups list { id: int, name: string, category: string } for the "Other group" picker and the rules form.

Contract

  • Request responses (list, detail) add approval: { decision: "auto_approved" | "needs_buyer", decided_by: "system" | "user", decided_at: datetime | null, net_total: decimal string, limit: decimal string | null, reasons: Reason[] }.
  • Reason: { code: string, message: string, line_id: uuid | null }. Codes: under_limit, over_limit, no_limit, no_total, totals_mismatch, group_rule_overridden, group_low_confidence, cheaper_catalog_ignored, edited_over_limit. The last three group codes are proposals.
  • Statuses stay as they are: approval_status is pending | approved | rejected, status is open | in_progress | closed. Auto-approval sets approved, approved_by: null, approval.decided_by: "system".
  • Before submit: POST /requests/approval-check takes the draft (lines, commodity group, flags) and returns the same approval object without saving. Save recomputes it; the preview is a hint only.
  • Setting: organizations.settings.approval = { auto_approve_below: number | null, always_to_buyer: { group_rule_overridden: bool, group_low_confidence: bool, cheaper_catalog_ignored: bool } }. Net EUR, strictly below. null means no limit. Totals mismatch is not a setting, always on. Read and PATCH (merge) through the existing org settings endpoint, admin only.
  • Activity: one RequestActivity on create or edit, action: "auto_approved" | "sent_to_buyer", detail: { net_total, limit, reasons }.
