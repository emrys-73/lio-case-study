Rule shape, agreed 10 Nov

  • Rule: id, keywords and commodity_group_id.
  • id is set by the server and never changes. The activity log points at it.
  • reason is optional. Empty by default. Shown to people and agents when given.
  • max_amount is optional. The rule only hits a line at or under that total. Made for "small" software. The number waits on Acme.
  • Full shape, matching and order: Rules and settings ↗.
  • Keywords can't be empty: an empty rule would match nothing, or everything.
  • Stored in org settings under commodity_rules. No rules is fine: empty list.
  • One function every path calls: categorise(db, organization_id, text) → group or none.
  • Rename anything and only the tests change, nothing else is built yet.

How the prompt works today

  • One prompt does two jobs: read the PDF and pick the group.
  • It picks one group for the whole request, not per line.
  • Acme's rules have nowhere to go. At best they'd be more hints in a 2,000-line prompt.
  • Hints in a prompt are a suggestion. "Non-negotiable" needs code.
  • Manual requests skip all of this. No suggestion at all.
  • Can't test parts on their own: a wrong group could be bad reading, a bad pick, or a missing rule.

Proposed: split it, rules first

Agreed 10 Nov

  • Extractor (Problem 1): reads the PDF only. No group list, so the prompt loses ~27k tokens. Strict structured output, nulls allowed. Gets the buyer's name so vendor and customer don't swap.
  • Categoriser: plain code. Every path goes through it: PDF, typed or agent.
  • Rules first: Acme's typed rules from org settings. A hit wins and the classifier never runs. Saves a call and can't be overruled.
  • Shortlist: code, not AI. About 15 of the 380 real group names. Shared with Problem 2. How it searches is picked by an eval: Shared search ↗.
  • Word match always works with no API key, so tests stay offline and nothing changes in the database.
  • Classifier: sees short aliases G1…G15 plus NONE, locked by the output schema. Code maps them back to real IDs. It can't return an ID that doesn't exist.
  • Every save re-checks rules, create and edit. The dropdown or an agent can't get round them.
  • Override: only a buyer or admin can keep a different group. It is logged with the rule ID.
  • Every result says why: rule, model or person.

One limit from "no schema changes"

  • A request holds one group, not one per line.
  • So line hits must collapse to one group. Agreed 10 Nov:

    • Lines hit different rules → the rule on the highest-value line wins, and it's flagged.
    • No rule → the classifier picks one group for the request.
  • Per-line groups need a new column. Logged for later.

Decisions before any code

  • Decided 10 Nov: check with Acme first, no new groups and no schema changes until they confirm.
    • Why: the group list and the database schema are shared by every company. A change made for one customer on a guess lands on all of them.
    • A product patched customer by customer turns into a monster nobody can maintain. So we fix Acme with settings only, and change the shared parts once we know it's right.
    • "IT Hardware": mapped to the existing group Hardware (29), under Information Technology.
    • "Office Supplies": doesn't exist. Small software subscriptions go to Office Equipment (15) as a stand-in, to confirm with Acme.
    • "Small" software: a line total up to €500, a placeholder in max_amount, to confirm with Acme.
    • All three live in Acme's settings, so their answer is a settings change, not a deploy.
  • Decided: rules beat the model, enforced on every save. No IReRa. No schema changes. Structured outputs. Rules built first. One group per request; the highest-value line's rule wins.
  • Decided 10 Nov: a buyer or admin can override a rule hit, logged. Rules carry an id and an optional max_amount. Two rules on one line: list order wins. Keywords work in German and English. Settings reads are tolerant, writes are strict, saves merge.
  • Prompt hints 15, 43, 31, 30 (decided 10 Nov): kept as hints in the classifier prompt, by name, no hard-coded IDs.
    • Not turned into rules: we don't know where they came from, so we won't enforce them.
    • Company rules always win. Hints only guide the model when no rule matches.
    • Each hint gets eval cases, so we see if the model follows it.
  • Clean up the padded list now, or leave it and only add rules?
  • Group per line: needs a schema change, so later.
  • Who manages the rules: Acme or us?
    • Us: set through settings and the API. No new UI. Acme sends changes, we apply them.
    • Acme: their admin needs a screen to add, edit and remove rules. See "Later" below.
    • Either way: admins only, every change logged.
  • Build order: rules first (fixes Acme on their own), then split the prompt.

1

Target design: works at millions of rows

The list is never sent to the model. Find a few candidates with cheap, indexed lookups, then let the model pick from those only. The prompt stays the same size at 2,000 or 2 million rows.

1. Exact matches first (no AI)

  • Company rules (Acme: cable ties → Electrical Engineering).
  • Supplier article number or EAN.
  • Past decisions: same company, same item text → same group.
  • Instant and certain at any size. Many lines end here.

2. Find candidates (no AI)

  • Keyword search on names and codes: "HP 305A", "Kabelbinder 200mm".
  • Meaning search (embeddings, stored once per row): "Kabelbinder" ↔ cable ties, "Notion team plan" ↔ software subscription.
  • Filter first by company, supplier or top-level category.
  • Combine both, keep the top 20–50. Milliseconds at millions of rows. Postgres with pgvector can do this.

3. Model picks from the shortlist

  • Gets the line item and ~20 candidates, never the full list.
  • Must return one of those IDs, checked in code, plus a confidence.
  • Can't invent an ID. Anything off the shortlist is rejected.

4. Low confidence → a person

  • They pick from the same shortlist, not a 2,000-option dropdown.
  • Their choice is saved and becomes an exact match next time.

Shrink the problem up front

  • Clean up the padded list: one "Toner Cartridges" group, with Bulk or Pallet as attributes. About 5× fewer rows.
  • Use the hierarchy: pick the top-level category, then search inside it.
  • Same pattern solves Problem 2: suggesting catalogue articles is the same search over a bigger list.
2

Try OpenAI's Decisions API for step 3

A new OpenAI endpoint (/v1/decisions, DevDay 2026) built for this exact job: we pass a question and a list of choices, it returns one of them.

  • Fits step 3: the shortlist becomes its choices, so the answer is always one of our groups.
  • Claims: about 10× faster than a normal call, image input too. OpenAI's own numbers, not checked by us.
  • Open: preview or beta status, pricing, and whether its scores work as a confidence for step 4.
  • How to judge it: run the same eval against our step 3 call, compare accuracy, speed and cost.
  • Not now: one model only (GPT-6 Luna), new and changing. Rules and the shortlist come first either way.
3

A screen to manage rules

Needed only if Acme manages its own rules. Lives on the Organization page, next to required fields.

  • List: each rule shows keywords, group and reason.
  • Add or edit: keywords as chips, group picked by search (not the 2,000 dropdown), optional reason.
  • Try it: type an item, see which rule hits before saving.
  • Remove: with a confirm.
  • Who: admins edit. Buyers and requesters only see the rules.
  • History: who changed which rule, when.
  • On the request: the group shows "Set by Acme rule" and the reason.
4

Top 3 suggestions and learning from picks

A person in the loop without slowing anyone down.

  • Show the top 3: the first is pre-selected, the other two are one click away. No 2,000 dropdown.
  • Show why: rule, model or person, with the reason.
  • Record the pick: which suggestion was shown, which was chosen.
  • Review it: if people keep picking #2 over #1, or keep overriding a rule, change the rule or the ranking.
  • Feeds the eval: real picks become new test cases.
  • Needs a place to store picks. Check first whether the activity log's JSON is enough before adding a table.
