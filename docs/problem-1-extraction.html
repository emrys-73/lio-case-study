What the key says is right

  • Total is the net cost Acme pays: items plus shipping and fees, before VAT.
  • Shipping and fees are lines, so the lines add up to the total.
  • Alternatives are not lines. Neither are headings with no price.
  • VAT ID: same letters and digits. No VAT ID on the quote means empty is right.
  • Vendor: the company that sent the quote. Umlauts and case ignored.
  • Numbers: equal to the cent.
  • Title, department and group: logged, not scored.

What is really going on

Acme's three complaints map to seven causes. Most are ours, not the model's.

1

Our schema causes every crash

"sometimes the upload errors out completely"

  • All 6 baseline crashes: model answers vatId: null, our schema wants text.
  • Hoffmann has no VAT ID. There the model was right.
  • styleGREEN has one, in a footer that is a picture. The model never saw it. See cause 7.
  • In 6 of 6 crashes the reply was usable. We threw it away.
  • Same for every model. A bigger model does not help.
  • This one bug is 40% of uploads on this set.
2

Nobody defined what "right" is

"Fields come out incorrect"

  • The prompt says "Total (Gesamtsumme)". The model gives the gross, as told.
  • The prompt says "Extract ALL line items". The model adds alternatives, as told. 9 of 9.
  • Shipping in the totals block is not a "line item". So it is dropped.
  • "Department/Customer" gets the customer, a person, or "Kunden-Nr.: 57692".
  • All three setups make the same errors. The model follows a vague spec.
3

The model does not know who the buyer is

  • styleGREEN prints the customer's address on top, the vendor only in the fine print.
  • Every model picks the customer as the vendor.
  • With layout text, gpt-4o-mini does it on Apple and Dream in Green too. Vendor drops to 3/15.
  • We know the buyer. It is the tenant (Acme). We never tell the model.
4

The model does sums, and nothing checks them

  • Totals that appear nowhere: €17,230, €1,867.26, €4,099.
  • Lines add up to the total in 0 of 27 runs that returned data.
  • The code never checks qty × price, or lines against the total.
  • Reading numbers is fine: 100% right on every found line. Adding them is not.
5

JSON only by asking nicely

  • No response_format. 1 of 45 runs wrote 1.546.99 and broke the JSON.
  • Rare now. It grows with more and messier quotes.
6

Every call pays for 2,000 groups

  • About 97% of the 24.8k input tokens are the commodity list.
  • Slow (10 s on mini) and noisy. Belongs to Problem 3.
7

Some of the quote is a picture

"fields are left empty"

  • Found by Adrian while checking the answer key, 10 Nov.
  • styleGREEN's letterhead and footer are one background picture per page.
  • The footer holds the VAT ID (DE271073640), the legal name and the address.
  • pypdf reads only real text. So does pdftotext. Neither returns the footer.
  • OCR on the page reads it right. Checked with tesseract.
  • This also feeds cause 3: the vendor's name and address are in the picture.
  • My first answer key said "no VAT ID". It was written from the text, not the page. Fixed.

Ruled out, on these 5 quotes

  • The text layout. Keeping columns (pdftotext) did not help. It made the vendor worse.
  • Not ruled out: text that is a picture. No text reader sees it. See cause 7.
  • The model size. gpt-4.1 made the same errors. It found more shipping lines and was 3× faster.
  • German numbers. Read right every time.
  • The config says bigger models were "slower without a real quality gain". Not true for gpt-4.1: same quality here, 3× faster.

To build: read the text in pictures

Built 97820f2. Design agreed with Adrian, 10 Nov.

What was built

  • A new upload route that reads the PDF and runs OCR on every page.
  • Full-page OCR skipped styleGREEN's footer picture. Cropped letterhead and footer strips read it.
  • Page pictures go to the model only when a page has no text, or vendor or VAT ID stay empty. Fired on 3 of 15 runs, all Hoffmann.
  • Two eval runs: without strips 7/15 fully right, with strips 9/15.

Step 1, on every upload, no model cost

  • Turn each page into a picture and OCR it on our server (tesseract, German).
  • Compare the OCR words with the text pypdf returned.
  • Add only the missed words to the prompt, under their own label ("text found in pictures").

Step 2, only when needed

  • Send the page picture to the model when a page has no text at all (a scan).
  • Or when vendor or VAT ID still come back empty after step 1.
  • Never for every upload. A page picture costs about as much as the whole call today.

Rules we did not pick

  • "The PDF has a picture": fires on 4 of 5 quotes. Most are just logos.
  • Retry only on empty fields: misses confident wrong answers, like the vendor swap.

Eval first

  • The styleGREEN key now expects DE271073640. Today that fails 3 of 3.
  • Write the failing test before the code.
  • Done when: styleGREEN VAT ID right 3 of 3, no score drops on the other 4 quotes, cost per quote logged before and after.
  • Log per run whether step 1 added text and whether step 2 fired.

Watch out

  • The backend image needs tesseract with German, and a page renderer (poppler).
  • OCR misreads umlauts ("Héhenkirchen"). It read the VAT ID right.
  • A logo can hold the vendor name. Check that step 1 catches it on styleGREEN.
  • Picture prices here are from memory. Confirm on OpenAI's price page.

With more time

A proper eval system with a human in the loop. So the eval grows with real use.

  • Review queue: a human checks the fixes, and they become new cases.
  • Version everything: prompt, model, schema, answer key. Every result says which.
  • Run it in CI. A change that drops the score does not ship.
  • Track it per customer. Acme's real quotes, scans included.
  • Spot checks in production: sample live runs for human review each week.
  • A reasoning log for every AI decision. For each field: the value, where on the page it came from, and why. Stored with the extraction. When a value is wrong we open the log, see what went wrong, and know what to fix.

The form is the safety net. The extraction does not need to be perfect, so long as the person sees what to check and can fix it. Built now: alternatives shown with "Add as a line", missing prices filled from the line total and marked, a warning on the line that does not add up, the totals warning under the total, department from the profile. Later:

  • The quote next to the form. The PDF beside the fields, so checking a value takes one glance, not a second window.
  • Show where each value came from. Click a field, the PDF jumps to the spot and highlights it. Needs the reasoning log above.
  • One-tap fixes for a mismatch. "Add the missing €X as a line" or "use the quote's total", instead of finding the line by hand.
  • Confidence per field. Mark the values the model was unsure of, so the person checks those first.
  • Pick an alternative. Swap a line for one of the quote's options, not only add it.
  • Learn from corrections. Every request stores what the extraction returned. Compare it with what was saved, and each correction becomes a new eval case.
  • Vendor from the VAT ID and bank details. So a quote addressed to someone else does not swap vendor and buyer.
